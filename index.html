These are results from the sample project of jvm-perf-lab, a set of JMH profilers, a Java agent and command-line tools for finding out what a change to a JVM program did to its performance, and why. The sample's benchmarks are small, and each has a known cause for its slow case, so the results below show what each tool reports when the cause is known.

Ideas

Measure with counts, then locate with profiles

Time per operation varies from run to run with CPU frequency, other load and GC timing. Instructions and cycles per operation, counted on the benchmark thread only, vary much less, so they show smaller changes. Once the counts show what changed, a flame graph of the same event shows where in the code it happens.

Compare variants within one JVM

A paired campaign switches a benchmark between variants from one iteration to the next inside a single fork, in a balanced order. The variants share the JIT's compiled code, the heap and the machine's state at that moment, so the difference between them is not mixed up with differences between JVMs.

Keep the benchmark apart from the JVM's own work

Counters are reported for the benchmark thread separately from JIT compiler threads, GC threads and other processes.

Look at the whole run over time

A timeline shows each fork from JVM start to exit: startup, warmup and measurement iterations, GC pauses and, with counters, cycles and IPC per 50 ms.

Count who calls what

A caller audit counts the calls reaching chosen methods, grouped by caller, from probes woven in as classes load.

Where to start

  1. The counters table. Compare memory-chase with memory-sequential: a similar number of instructions per operation, but the pointer chase through a shuffled array runs at about 0.08 instructions per cycle against about 4.5, and takes about 50 times as long. branch-random against branch-sorted: about 75 against 0.04 branch mispredictions per 1,000 instructions, and about 10 times as long.
  2. The paired timelines. memory-paired and branch-paired alternate the two settings within one fork; IPC drops in every shuffled or random iteration.
  3. Where the misses land. The kperf runs memory-chase-kperf (cache misses) and branch-random-kperf (branch mispredictions); open reverse to see the methods where the events land.
  4. Ordinary profiles. wordcount-async has CPU and allocation flame graphs; its benchmark marks each op's count and look-up as spans, and the CPU graph's span panel splits the samples by them. The campaign maps-async compares a HashMap against a TreeMap: both flame graphs and the differential ones, as tabs.
  5. A run with several forks. The timeline of wordcount-2-forks-xctrace-ipc shows both JVMs from start to exit, with counters during measurement.
  6. A caller audit. The audit report counts calls to WordCount.normalize by caller and call site.

Terms

Run
One JMH invocation under one profile: a section under Runs. Its name is the benchmark setting and the profile, e.g. memory-chase-kperf.
Fork
A JVM that JMH starts to run the benchmark: warmup iterations, then measurement iterations.
Profile
What records the run. async-profiler: flame graphs of CPU time, allocation or wall-clock time. kperf: flame graphs of PMU events (async-profiler with kperf events). xctrace: PMU counts per operation through Apple's xctrace. audit: the caller audit. none: JMH's own results plus allocation and JIT activity.
PMU counter
A CPU hardware counter: cycles, retired instructions, cache misses, branch mispredictions. IPC is instructions per cycle. /k means per 1,000 instructions.
Campaign
A comparison of variants over several rounds, with a report: under Campaigns. A variant is one of the settings being compared; a cell is one variant in one round. In a paired campaign, the variants alternate within one fork.
